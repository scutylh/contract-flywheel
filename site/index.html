01 · 飞轮总览

同一个系统，三圈迭代，人逐步退出执行层

每一圈的输入都来自上一圈的真实使用反馈；每一圈的产出——Skill、组件、约束、能力边界——都沉淀为下一圈的资产。点击任意一圈查看完整执行回放。

主角不是功能，是持续改进的结构

飞轮不是转一圈就停：每一圈的沉淀物——Skill、组件、约束、评估用例——直接成为下一圈的起点资产，所以三圈做同一套系统，人重复做的事越来越少、自治边界一圈比一圈大。持续改进不是口号，是这个回路的结构。

背后的 3-5 年愿景（折叠，非本页主体）

Agent = 代码 + 提示词，二者皆可由 AI 构建，因此 Agent 亦可由 AI 构建。短期（0-1 年）打通需求到开发的 AI 闭环；中期（1-3 年）常规流程自主交付、标准化 MR 由 AI 审核；长期（3-5 年）全链路自治。本页演示的是短期目标的第一个切片。完整文档见仓库 docs/vision.md。

03 · 工程设计

让比例变化可信的三块地基

飞轮能转起来，靠的不是模型能力突进，而是权限、回放评估、资产沉淀三套机制让每一步都可控、可复盘、可复用。

权限模型：动作 × 风险 × 审批人

原则是「不可逆性越高，人越靠后但永不缺席」——写代码可以自治，改规则永远人工。

能力边界表：自治权是挣出来的

每一圈结束更新一次：任务类型、当前自治级别、历史成功率、进入下一级的准入条件。这是「Agent 能自主解决的边界」的显式记录。

回放与评估：每一步都可复盘

全部执行过程落 trace（步骤、输入输出、人工确认节点），支撑三件事：
Case 级回归每次提示词/组件变更，重跑历史评估集（本演示已积累 50 份合同回归集 + 13 条用例），绿了才允许合并。
失败案例沉淀人工审核打回的每一处修改（如圈 1 的金额大小写冲突）转为评估用例，进入 Skill 的约束条件。
灰度与回滚提示词版本化管理，新版本先跑回放再上线；线上异常按 trace 定位到具体步骤，一键回滚到上一版本。
04 · 入职 90 天

把本演示的三圈，换成真实中台的三圈

贴着现有中台（HR / 薪资 / 报销，已有真实用户）推进，合同审核可作为第四个切片接入。

DAY 1–30

摸清家底，立最小基建

  • 梳理现有中台架构、数据接口与高频业务动作清单
  • 落地 trace 记录与回放的最小基建（本演示的 harness 即雏形）
  • 选一个报销/合同高频场景，跑通「会议纪要 → 需求单 → Issue」
DAY 31–60

跑通真实版圈 1–2

  • Agent 基于 Issue 完成工作流开发，全部 MR 人工审核后上线
  • 建立权限模型 v1 与澄清式交互规范，接入真实组织角色数据
  • 沉淀第一批 Skill、组件与评估用例，能力边界表开始记录
DAY 61–90

开放第一个自治任务类型

  • 1–2 个低风险任务类型进入「Agent 开发 + Agent 评审 + 人工确认」自治交付
  • 回归测试体系 v1：Case 级自动验证 + 提示词版本管理
  • 输出自治交付成功率与边界数据的第一个月报
05 · 附录

这份作业本身就是一次 harness 实践

本作业的开发方式

  • 设计目标（人）：确定三圈叙事、场景选题与页面结构，即本文档的 PLAN。
  • 执行（Agent）：页面代码、轨迹数据组织与素材初稿由 Agent 生成。
  • 审查接管（人）：所有业务语义、数字与结论由我本人逐条审校后确认。

诚实声明：本页三圈演示中的业务数据为模拟数据；执行轨迹由自研 mini-harness 组织，LLM 调用以录制 fixture 回放呈现，关键内容完整、次要部分以省略号略去。选择回放而非实时调用，是为了让评审任何时刻打开都看到一致、可复盘的过程——「可回放」本身就是工程目标之一。
