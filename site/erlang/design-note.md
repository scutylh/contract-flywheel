# 二郎 Erlang · 需求澄清工具 — 设计说明

副标题：从模糊的原始信息到可落地的需求文档。

## 一、为什么做这个

软件开发最贵的一环，是从「人说的话」到「能写的代码」之间的鸿沟：需求散落、理解漂移、文档落地不了。二郎负责前半段——把「听懂需求」这一步做成产品：多源信息 → 多 Agent 协作澄清 → 可落地的需求文档。

## 二、产品定位

二郎是「开发流程 AI 化」的前半段。它产出需求文档后，交给主项目的开发自动化流水线（后半段，见 automation.html）——先听懂需求，再自动开发。

## 三、三个核心能力

### 1. 分层记忆（多源归一化）

多源接入不是目的，是原料。会议记录文本、聊天记录、扫描件、录音四类原始材料进来，先归一化——统一转成文本、对应原始文件，再进分层记忆：

- 摘要层（索引）：结构化抽取，供 Agent 高效沟通
- 原始层（证据）：每条摘要可回溯到原始文件的具体段落（如「聊天记录 #1」）

关键设计：摘要不是「一次性压缩」，而是带原文锚点的结构化抽取——摘要做索引，原文做证据。

### 2. 多 Agent 协作

四个 Agent 各持一方信息，接力协作、互相纠偏——不是吵架，是各司其职的流水线：

| Agent | 持有 | 职责 | 收敛 |
|-------|------|------|------|
| Analyst | 会议原始记录 | 整理并出需求草稿 | 意图一致 |
| Coder | 代码仓 + Skill | 核对代码现状 | 现状吻合 |
| Estimator | 历史周期 / 预算 | 评估周期预算 | 资源可行 |
| Verifier | 业务规则 / 权限 | 终审权限合规 | 权限合规 |
| E … | 可扩展 | 更多视角 | — |

### 3. 持久存储

按项目制沉淀三层数据：原始文件层 → 项目进展层 → 细节展开层。每次澄清的原始文件、项目、session 都留痕，持续改进由此而来。

## 四、场景设计：金蝶合同单字段提取

贴合「财务领域 Agent，封装金蝶」：客户用金蝶云星空管合同，但合同单字段靠人肉填。需求是「在金蝶合同单据之上，自动提取金额 / 账期 / 付款条件回填扩展字段，走金蝶现有审批流」。协作的价值被量化：需求从「新建系统」澄清成「回填扩展字段」，周期从 2 周砍到 3 天。

## 五、演示方式

- 纯静态 HTML/CSS/JS，零后端依赖
- 群聊形式（微信 / 飞书风格），自动播放 + 重新播放
- 流程：项目经理 Lyn 发起 → Analyst → Coder → Estimator → Verifier → 项目经理确认 → 流程工具提单
- 对话写死在 data.js 里做回放，不接实时 LLM

## 六、技术实现

- 演示版（本页）：纯静态、数据驱动（data.js + app.js）
- 生产版（架构不变）：真实 LLM 多 Agent + 后端服务 + 评估集
- 评估优先：评估集和回归测试是系统有效性的证明

## 七、与主项目的关系

本 demo 产出的需求文档（REQ-2026-0047），交给主项目的开发自动化流水线（automation.html），串成「需求澄清 → 开发自动化」的完整链路。
